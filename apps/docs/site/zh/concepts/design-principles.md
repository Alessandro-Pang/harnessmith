# 设计原则

这里不列抽象口号，而是按「问题 → 决策 → 代价」解释主要取舍。每条原则都对应一个会反复出现的工程问题；代价也一并写出，方便判断某个看似合理的功能为什么没有纳入当前范围。

每条原则按三段展开：**问题** 是当时面对的困境，**决策** 是最终采取的立场，**代价** 是这个立场放弃的东西。

## 本地优先：个人工作方式不应先依赖云端控制面

**问题。** 个人规则、任务历史和项目线索可能包含敏感路径或工作习惯；如果核心流程必须连接远端服务，离线、隐私和可迁移性都会变差，而且你无法审计数据去了哪里。举个实际的场景：你在飞机上打开 Codex，想继续昨天的跨仓库重构。如果规则路由和 Memory 在远端，你连「上次做到哪了」都查不到。

**决策。** Harness、Memory、Task 与受限 audit 默认保存在本地文件系统，用 schema 和 CLI 管理。所有状态都是你能打开看的文件，不是远端黑盒。`~/.agent-harness` 是你的个人规则与跨仓库关系，`~/.agent-docs` 是你的跨项目 Memory，`<project>/.agent-docs` 是项目工作状态——全部是本地目录，你可以用 `ls`、`cat`、`grep` 直接查看，也可以用 `export` 打包带走。

**代价。** Harnessmith 不提供跨设备云同步、集中式团队策略或可信远程 attestation；这些能力如果需要，应由显式选择的外部系统承担，而不是悄悄内置。本地优先意味着你换机器时要做一次 `export` / `import`，而不是自动同步。这是有意为之，不是功能缺失。

## 宿主中立，但不假装宿主相同

**问题。** 个人方法值得跨宿主复用，但不同 Coding Agent 的路径、规则格式、激活机制和权限系统确实不同。假装它们相同，要么做出最低公共分母的受限版本，要么在细节上默默出错。比如 Codex 的规则入口在 `~/.codex/AGENTS.md`，Cursor 在 `<project>/.cursor/rules/` 下以 `.mdc` 格式存在，Claude Code 在 `~/.claude/CLAUDE.md`，路径和格式都不同，不能简单复制。更有趣的是，同样的规则文本在不同宿主中的生效方式也不同：Cursor 的 MDC 规则可以设置为 `always` 模式，Codex 的全局规则默认每次会话都加载，而 Claude Code 的 `CLAUDE.md` 由项目上下文决定何时引用。

**决策。** 通用内容留在内嵌 Runtime，差异进入外层 Adapter；capability descriptor 明确记录每个宿主的 scope、activation 和 owner，而不是把它们抹平。当你在 Adapter 里看到 `"scope": "global"` 和 `"activation": "host-default"` 时，这两行背后是 Adapter 对宿主路径、环境变量、规则格式和激活机制的具体实现。但这些细节被封装在 Adapter 内部，不污染通用 Harness 模板。

**代价。** 新增宿主不能只复制一个目录完事，必须逐一验证其官方路径契约和真实行为，这也是支持列表增长保守的原因。每个新 Adapter 都要经过完整的 preflight 测试（dry-run、安装、状态、内嵌 Runtime 校验和卸载），没有捷径。

## 渐进披露：让入口成为地图，而不是百科全书

**问题。** 历史文档需要保留决策和演进记录，但把全部历史与流程常驻上下文会迅速增加成本：关键边界淹没在过期、弱相关或互相冲突的内容里，错误召回和幻觉风险同步上升。一个典型的陷阱：你在 `AGENTS.md` 里塞了 500 行，包含安全规则、每个仓库的发布流程、三套不同时期的测试命令、两条已经废弃的 CI 配置说明，每次对话这些内容都被加载进上下文。Agent 在 500 行里找到真正相关的 20 行，不仅要花掉上下文预算，还可能被过期信息误导。

**决策。** `AGENTS.md` 只保留高损失规则和发现顺序；route 先返回一个主要 playbook 与必要 topics；search 先给命中摘要，再按需读取正文。入口文件控制在 50 行以内，具体流程在需要时由文档路由按 `--intent` 精准加载。这样做的好处是：入口永远可读，Agent 不会因为历史内容过载而漏掉关键红线，历史文档仍然完整保留在 `docs/` 和 `.agent-docs/` 中供追溯。

**代价。** 文档必须持续维护 metadata、状态、索引和清晰路由；没有入口的孤儿文档等于不存在，保留下来的历史也必须始终能与当前事实区分。渐进披露的前提是「每篇文档都有明确的元信息和路由」，这需要持续的文档治理，不是写完就完了。

## Guidance 与 Enforcement 分离

**问题。** 自然语言规则很有用，却不能保证模型每次都遵循。把「文档写了」说成「系统强制」，会制造虚假安全感，出事时才会发现文档本身没有约束力。比如你在规则里写了「禁止执行 `git push --force`」，Agent 在对话里也确认了这条规则，但宿主权限系统没有限制网络访问，模型在某个版本的推理中仍然可能执行。

**决策。** 建议写入规则和 playbook；必须成立的约束写入 SafePath、schema、状态机、测试、CI 或宿主权限系统。哪一层保证什么，就明说在哪一层。Harnessmith 的文档可能说「远端写入需要明确授权」，但真正阻止写入的是宿主 sandbox 和权限系统。Harnessmith 在文档里写清楚这一点，不假装自己有能力强制。

**代价。** 某些跨宿主行为只能声明为 advisory 或 delegated，无法靠统一 Markdown 获得强制性。比如「发布前必须通过全部测试」这条规则，在 Codex 里是自然语言建议，在 CI 里是机械门禁。Harnessmith 可以帮你把测试命令写进规则，但真正挡住未通过测试的发布，靠的是 CI 配置里的 `&&`，不是 Markdown 里的文字。

## 安全失败与可恢复变更

**问题。** 配置安装器一旦覆盖用户文件或留下半完成状态，损失远高于一次安装失败。用户失去的可能是一年攒下的规则。比如你已经在 `~/.codex/AGENTS.md` 里维护了 200 行经过反复验证的规则，一个安装脚本直接覆盖了它，而且没有备份。

**决策。** 无法证明目标可安全接管时默认拒绝。install、restore 与 uninstall 共享 containment、路径段检查、锁、完整预检、备份和精确回滚。每个写入操作都经过 7 步安全检查（canonicalize → 校验 containment → lstat 拒绝 symlink → 获取操作锁 → staging → 提交前全量复检 → 失败精确回滚），任何一步失败都会停止，不会留下半完成状态。

**代价。** 流程更保守，遇到 unmanaged 或 modified 文件会要求用户先理解差异，而不是自动接管。这意味着你需要多花几分钟看 dry-run 输出，但换来的是一份确定可以回滚的安装记录。

## 状态帮助工作，但不篡位事实源

**问题。** 跨会话任务需要持久状态，但历史记录会过期，也可能只是当时的推断。昨天成立的结论，今天可能已经被一次 rebase 作废。比如 Memory 里记录着「项目使用 npm 作为包管理器」，但上周有人迁移到了 pnpm；如果 Agent 直接复用这条 Memory 而不核对 `package.json`，接下来所有命令都会用错工具。

**决策。** Memory 被定义为非权威线索；Task 是工作契约和证据账本。当前结论仍要回到代码、配置、测试、schema 与正式文档核对。Memory 的数据结构里有一个 `source-of-truth: false` 字段，明确标出它不是事实源。这不是谦虚，是设计出来的安全机制。

**代价。** 系统不会自动把每次经验提升成长期规则；沉淀需要明确目标和复核，省不掉人的判断。你可以把 Memory 里的线索手动提升为正式规则，但要走 proposal → review → apply 的流程。不能一次对话就把「今天发现 X 项目用 pnpm」自动写进规则，因为明天可能又改回去了。

## 声明必须绑定相称证据

**问题。** 「本地测试通过」「真实 Host 运行过」和「候选可以发布」回答的是三个不同的问题，混用它们就会得到一个什么都证明不了的「全部通过」。比如在一次发布中，单元测试全绿、lint 无警告、覆盖率达标，但从来没有人在真实宿主里跑过安装流程。这三个绿色检查加起来，证明不了「用户运行 `npx harnessmith` 能成功」。

**决策。** 公开能力分为 implemented、delegated 与 unsupported；验证分为确定性仓库门禁、Host Eval、记录校验和人工复核。受限阴性结果使用 `inconclusive`，不冒充结论。四个验证层级各司其职：门禁管仓库内部一致性，Host Eval 管真实宿主行为，记录校验管证据格式，人工复核管语义判断。

**代价。** 发布说明必须保留未验证范围，不能用一个总的通过状态替代证据解释。每次发布时要写清楚「本次哪些宿主完成了 Host Eval、哪些只通过了仓库门禁、哪些标记为 inconclusive」。写起来麻烦，但读的人知道信到什么程度。
