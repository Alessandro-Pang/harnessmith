# 内容与双语策略

本文规定文档的事实来源、页面结构、双语范围、更新触发器和生成边界。贡献者按它维护内容；普通读者可以用其中的优先级判断文档与实际行为不一致时该信谁。

把这件事写成一页明确的策略，而不是散落在各处的口头约定，是因为文档系统的失败模式几乎都一样：一开始只有几页，谁改什么都清楚；等页面多起来、语言多起来，「我刚改的这句话还有哪里需要同步」就变成纯靠记忆的问题。这页策略的作用，是把记忆变成可检查的规则。

## 内容层级

| 层级 | 目标 | 内容边界 | 典型读者 |
| --- | --- | --- | --- |
| README | 首次理解与最短成功路径 | 定位、宿主、安装、常用操作、安全摘要与导航 | 第一次接触项目的人 |
| 文档站点 | 使用、设计和维护知识 | 指南、架构、边界、CLI、迁移与参考资料 | 日常使用者与贡献者 |
| 代码与 schema | 可执行契约 | 实际行为、字段、默认值与拒绝条件 | 需要核对行为的人 |
| 测试与 CI | 可验证证据 | 回归、内容契约、链接和构建门禁 | 维护者与评审者 |

这四层的关系是「上层描述下层，下层约束上层」。README 和站点描述行为，但行为的最终裁决者是代码和 schema；测试把描述与行为钉在一起，任何一层偏离都会在某条断言上爆出来。

发生冲突时，先核对用户当前意图，再以当前代码、配置、测试、schema 和 manifest 为事实依据。举一个具体例子：站点某页写着「默认超时 30 秒」，但 schema 里默认值是 60。此时 schema 赢，页面改。反过来，如果测试断言「文档必须写 30 秒」而代码已改成 60，那是断言过期，断言改。两个方向都有明确去处，不存在「文档和代码各执一词」的灰色地带。

## 页面结构

每篇公开页面按下面的顺序组织，页面可以按主题增删中间章节，但不要改变读者的基本阅读路径：

1. **先给结论和范围。** 开头用一到两段说明这页解决什么问题、适合谁，以及它不能证明什么。
2. **再给可执行内容。** 使用步骤按实际操作顺序排列；命令附带作用、是否写入、前置条件和失败后的下一步。
3. **随后解释原因。** 架构和设计页面采用「问题 → 决策 → 代价」；参考页面说明资料的用途和证据等级。
4. **最后保留边界。** 把宿主依赖、未验证项、废弃项和 `inconclusive` 条件写在结论附近，不把限制藏在脚注里。

页面 frontmatter 统一保留 `title`、`description`、`owner`、`audience`、`status` 和 `updated`。其中 `owner` 表示维护责任，`audience` 表示主要读者，`status` 表示当前页面是否仍是公开入口，`updated` 记录最近一次事实或结构调整日期。它们用于导航和维护，不替代正文中的事实说明。

写作时优先使用具体动作和结果，例如“运行 `status` 检查安装记录”；少用“可以帮助用户更好地完成”这类没有验收标准的句子。首次出现的术语给出中文解释并保留稳定英文标识，后文统一使用同一种写法。

文档需要描述计划时，必须与已实现事实分开。「计划做」和「已经做了」用不同的措辞，读者才不会把路线图当功能清单。这条规则看起来琐碎，实际是高发事故：一份写着「支持 X」的文档，如果 X 只是计划，读者会在真实宿主里撞上不存在的功能，然后对整个文档体系失去信任。

历史页面可以保留被替代方案和演进过程，但必须明确它们是在解释「为什么走到这里」，不能让读者把历史输入或后来采用的研究框架误认为当前实现契约。历史内容默认不应全部进入 Agent 上下文，应通过 metadata、状态、路由和检索按需发现。

## README 精简门禁

README 的职责是帮助第一次接触项目的人完成理解、安装和最短成功路径；精简不等于丢弃信息。每次从 README 删除内容时，PR 必须附带迁移清单，并把仍然有效、会影响使用或维护判断的内容放入文档站点。只有能够说明该内容属于重复、过时或纯实现细节时，才可以不迁移；不能因为内容技术性强、篇幅长或暂时缺少合适页面而直接删除。

为什么要把「删 README」这件事管得这么严？因为 README 是大多数人对项目的第一印象，也是被阅读次数最多的页面。一个常见诱惑是「这页太长了，砍掉一半」，但如果砍掉的是别人决策依赖的信息（比如某个宿主的特殊限制、某条安全边界），读者不会知道它曾经存在过，只会在踩坑之后才发现。「精简门禁」的要求因此不是「别删」，而是「删之前说清楚它去了哪里」。

迁移后应同时更新导航、站内链接和内容契约测试。若一项信息只适合由代码、schema 或 `--help` 承载，站点也应给出入口和适用边界，让读者知道去哪里核对，而不是让信息静默消失。删掉的每个字都应该有去向。

一个实际的迁移例子：假设 README 里有一段详细的环境变量说明，删掉它之前，先确认这些信息已经（或将要）出现在 `reference/cli.md` 或对应 Adapter 文档里，再在 PR 描述里列出迁移清单，最后检查站内是否还有指向旧位置的链接。三步都做完，这次删除才算完成。

## 双语范围

中文是深度技术文档的 canonical 版本；中文和英文 README 保持相同信息架构，英文站点维护完整的定位与快速开始。新增或修改公开能力时，必须同步两份 README 的核心声明、宿主列表、命令和安全边界。深度页面若尚未翻译，应链接到 canonical 页面，不能复制一份无人维护的过期全文。宁可明确告诉读者「这页只有中文」，也不要留一份悄悄过期的英文副本。

「不维护过期副本」这条规则来自一个常见反模式。假设某项目把英文页全部翻译了一遍，之后中文页持续更新，英文页却没人同步，半年后英文读者照着旧文档操作，处处对不上。比起「看起来国际化但内容过期」，「诚实标注这页只有中文」对读者更友好，至少他们知道自己在读的不是最新版，会主动去对照 canonical 页面或源码。

## Owner 与更新触发器

站点页面 frontmatter 的 `owner` 标识维护责任。以下变化必须同步相关文档：CLI 命令或默认值、Adapter 支持、路径与环境变量、schema 迁移、安全边界、发布门禁和能力证据。触发器列表的意义在于让「忘了同步」变成可检查的遗漏，而不是靠记忆。

举几个典型触发场景：给 CLI 增加一个新 flag，要检查 `reference/cli.md` 和相关 guide 是否需要更新；调整某个宿主的目标路径解析逻辑，`guide/hosts.md` 的表格可能就要改；修改 schema 默认值，所有提到该默认值的页面都要过一遍。契约测试会拦住一部分（比如关键页面缺失、导航断链），但措辞层面的同步仍然依赖作者在 PR 里自查。

## 手写与生成边界

所有 Markdown 页面和导航均为人工维护事实；VitePress 只生成静态 HTML、资源和本地搜索索引。`apps/docs/site/.vitepress/dist` 与缓存不提交。搜索索引来自同一构建输入，不是新的事实源。

同样属于人工维护、但不面向站点读者的内容放在仓库根 `docs/`：架构决策记录（`docs/adr/`）和内部提案留在那里，供贡献者追溯「为什么这么决定」。它们不进入站点源码目录，VitePress 不会看到它们。

这条边界展开说。有些项目会从源码注释或 schema 直接生成文档站点，看似省事，实际把「文档」降级成了「代码的投影」：读者读到的是字段列表，而不是「什么时候该用这个功能、有什么坑」。Harnessmith 的选择是：能机械验证的（链接、结构、关键措辞）交给测试，需要判断的（怎么解释、先讲什么后讲什么）留给人。

内部工作稿（如 `docs/optimization-plan.md`）放在仓库根 `docs/` 下维护：它们保留在仓库中接受评审，但不进入站点源码目录，自然也不会进入发布站点。草稿归草稿，发布归发布。这个区分的实际效果是：维护者可以在仓库里留下思考过程和未决方案，而不用担心读者把它们当成当前承诺。

## 本地搜索边界

站点使用 VitePress 内置搜索，在构建阶段生成随站点发布的本地搜索索引，不依赖服务端或外部搜索服务。这种方式部署简单、响应快，也能让搜索结果与当前文档版本保持一致，索引和页面出自同一次构建，不会出现「搜到的是旧版」。

选本地搜索而不是接入 Algolia 之类的托管服务，除了部署简单，还有一个隐私考量：搜索行为不离开读者浏览器，站点运营者也拿不到「用户在搜什么」的数据。对一个强调本地优先的项目来说，这是顺理成章的选择。

索引会随文档规模增长并下载到浏览器，当前方案也不提供向量语义召回。这意味着两件事：文档量如果翻好几倍，首次加载索引会变慢；用自然语言描述问题（「怎么让 Agent 记住上次的事」）可能搜不到只写了「Memory」的页面。未来如果文档规模或召回质量要求明显超过本地搜索能力，再在对应的搜索设计文档中比较分词、模糊匹配、相关度排序、预构建索引与语义检索方案。先承认边界，再讨论升级。
