# 贡献文档

项目通用贡献规则见仓库 [CONTRIBUTING.md](https://github.com/Alessandro-Pang/harnessmith/blob/main/CONTRIBUTING.md)。本文只补充文档站点的工作流：如何本地预览、提交前运行哪些门禁，以及如何让页面内容和代码契约保持同步。

为什么要单独有一页讲「贡献文档」？因为文档贡献和代码贡献的失败模式不一样。代码改错了，测试会红；文档改错了（比如删了一句别人依赖的说明、改了一个措辞导致读者误解），可能几个月后才有人发现，而那时已经有人照着错误描述操作了。这页契约的目的，是让文档改动也能像代码改动一样，在提交前就被拦住大部分问题。

## 本地运行

需要 Node.js 24.12.0 或更高版本与仓库声明的 pnpm 版本。装好依赖后启动开发服务器：

```bash
pnpm install --frozen-lockfile
pnpm run docs:dev
```

开发服务器默认在 5173 端口启动，支持热更新。改 Markdown 保存后浏览器立刻刷新，适合边写边看效果。如果你只改了一两处措辞，也可以跳过开发服务器，写完直接跑后面的检查命令。

生产构建和预览：

```bash
pnpm run docs:build
pnpm run docs:preview
```

`docs:build` 会执行完整的 VitePress 构建，包括死链检查和搜索索引生成；`docs:preview` 在本地起一个静态服务器，让你确认构建产物的实际效果。提 PR 之前至少跑一次 build，能提前发现大部分问题。

## 提交前检查

```bash
pnpm run docs:check
pnpm exec vitest run --config config/vitest.config.ts packages/cli/src/__tests__/docs-site.test.ts
pnpm run preflight
```

三条命令各管一摊：

- `docs:check` 跑 VitePress 构建加死链检查，确保站点能正常生成、内部链接全部有效；
- `docs-site.test.ts` 是内容契约测试，检查关键页面存在、frontmatter 有 owner、README 不超长度上限、最短可执行命令没变；
- `preflight` 是仓库级预检，包括 Markdown lint、类型检查和其他门禁。

VitePress 构建会生成本地搜索索引并拒绝无效的内部 Markdown 链接，死链在构建期就拦下，不会留到线上。内容契约测试会检查关键页面、owner 元数据、README 长度和最短可执行命令。三条都过，再提交。

如果契约测试因为你改动了「被锁住的事实」而失败，先别急着改测试。读一下失败信息，确认是事实变了还是你改错了。这个判断有时需要核对代码或 schema，但花这几分钟是值得的：测试锁住的都是曾经被验证过的事实，轻易解锁等于放弃了回归保护。

## 契约测试与文档事实同步

`docs-site.test.ts` 不只检查格式，它断言了一批当前事实：页面结构、标题措辞、关键链接路径、README 命令与长度上限。这套测试是文档的回归网，也是双刃剑。

当这些事实本身变化时（例如能力证据文件搬家、历史页标题修订），必须在同一次变更里同步更新测试断言，否则测试锁住的是过期事实。反过来，不要为了让文档改动「省事」而削弱断言：先判断是事实变了，还是文档写错了。事实变了就同步断言，文档错了就改文档——两个方向都有明确去处，唯独「删断言图省事」没有。

这条规则的背景是一个真实痛点：有些项目的测试会在重构时被「顺手」删掉或放宽，因为删掉比搞清楚「为什么会红」更快。短期看省了事，长期看测试套件逐渐失去意义，没人知道哪些断言还有效、哪些早就该更新。Harnessmith 的要求是：断言可以改，但改动必须和事实变化在同一个 PR 里，让评审者能一眼看到「事实从 A 变成了 B，断言也跟着从 A 变成了 B」。

## 写作要求

这些要求不是风格偏好，而是为了让文档在两年后仍然可读、可维护：

- 先写使用者需要做出的判断，再补实现细节。读者打开一页文档，通常带着一个问题：「我该怎么做」或「这个适不适合我」。先回答这个问题，再解释原理和细节。如果顺序反过来，读者得翻到底部才能找到自己要的东西。
- 能力声明使用「已实现 / 由宿主负责 / 不支持」，并链接到代码、测试或能力证据。避免「应该可以」「理论上支持」这类模糊措辞。读者需要一个明确答案，而不是一个需要自己去验证的猜测。
- 标注版本与时间边界；无法验证的结果使用 `inconclusive`。文档天然会过期，明确写「截至 v0.3.0」或「2026-09 时」，读者就知道该用多信任这段内容。`inconclusive` 不是「不知道」的客气说法，而是一个精确状态：我们试过验证，但受限于条件无法得出结论。
- 标题层级连续、链接文字有意义、代码块标注语言；交互元素必须保留键盘焦点。这些是 accessibility 的基本要求，也是让屏幕阅读器和键盘导航用户能正常使用文档的前提。
- 重要架构取舍写入对应的架构、边界或维护文档，并说明背景、候选方案、决定与后果。「为什么这么设计」是最难从代码里看出来的信息，也是最值得记录的信息。
- 内部工作稿（如提案、优化计划）放在仓库根 `docs/` 下，不进入 `apps/docs/site/`，也就不会进入发布站点。草稿可以留在仓库里供维护者参考，但不应该被读者误认为当前承诺。

## 部署

Pull Request 只构建站点。合并到 `main` 后，Docs workflow 才上传静态产物并部署 GitHub Pages；PR 本身不会主动发布，部署是合并之后的显式动作。目标站点为 <https://alexpang.cn/harnessmith/>。

这个流程意味着你在 PR 阶段可以放心实验：构建会跑，但不会发布。只有合并之后，变更才会对读者可见。如果合并后发现有问题，回滚 `main` 分支即可，下一次部署会自动恢复。
