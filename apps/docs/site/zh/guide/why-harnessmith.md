# Harnessmith 解决什么问题

装任何工具之前都值得先问三个问题：它解决什么问题，能解决到什么程度，使用它要付出什么代价。这一页按
「问题 → 方案 → 代价 → 适用范围」展开，方便你在安装前做判断。

Harnessmith 面向同时使用一个或多个 Coding Agent、并且打算长期维护自己工作方式的人。它不创造新的模型能力，
做的事说白了只有一件：把那些容易散落在配置、聊天和个人经验里的工作约束，变成一套可以安全安装、按需读取、
持续验证的本地工作层。

「本地工作层」这个概念可以展开。Harnessmith 的安装后工作层不依赖云端服务；它不是 IDE 插件，不绑定特定编辑器；也不是一套
提示词模板，随聊随丢。它更像是你给自己搭的一套工作环境：有明确的入口（规则文件）、有分层的内容（核心边界
在最前面，详细流程按需加载）、有状态记录（任务做到哪了）、有安全保障（装坏了能恢复）。这些东西单独看都不
新鲜，组合起来就是一个「可以长期演进的工作方式」。

先交代出身，免得对它产生错误的想象：它并不是先按一套 Harness Engineering 理论设计出来的。最初只是想把实际
项目中已经有效的 `AGENTS.md`、文档检索和工作记录方法抽出来，让它们可以跨项目、跨 Coding Agent 复用；
宿主、授权、Memory、生命周期和验证这些边界，都是在通用化过程中逐渐出现的。真实演进顺序见[历史与渊源](/concepts/history-and-influences)。

## 问题不是少写一份规则

设想一个常见的开局：你在 Codex 里规定「只读分析不能改文件」，过了两周在 Cursor 里补了测试命令，
又在 Claude Code 里记录了发布流程。又过了几周，三份规则各自演化，谁也不完整；换到新项目或新宿主时，
你已经说不清哪一份才是最新的，只能再口述一遍。

这个场景的痛点不是「重复劳动」，而是「漂移」。三份规则从同一个起点出发，随时间越走越远。你改了一处，
忘了另两处；或者在某个宿主里加了新规则，却忘了其他宿主也需要。几个月后，你已经不知道哪份是完整的、
哪份是过时的，只能凭记忆判断，而记忆恰恰是最不可靠的部分。

最直觉的解法是把所有内容合并进一个巨大的 `AGENTS.md`。这条路走不远：常驻上下文变长之后，最关键的安全边界
被大量细节淹没，模型反而更容易漏掉它们；而具体流程还是会过期，文件越长越没人敢改。真正需要管理的不是
「一份更全的规则」，而是一套系统：稳定入口、按需文档、宿主适配、可恢复安装、工作状态和验证证据。

「按需加载」是这套系统的关键。核心安全边界（比如「未经允许不能 push」）放在最前面，每次会话都加载；
具体流程（比如「发布前检查清单」）放在独立文档里，只有用到时才读。这样既保证了关键约束不被淹没，
又让详细内容可以充分展开，不必担心超出上下文预算。

还有一个容易被忽略的约束：历史文档不能为了缩小目录就直接删除。它们记录了决策和方案如何演进，丢了就再也
解释不清「当时为什么这么做」；但也不应该默认进入每一次对话，否则大量过期、弱相关甚至互相冲突的内容会
挤占上下文，增加误判和幻觉风险。所以正确的问题是「怎么保留历史、又只把当前需要的部分送进上下文」，
而不是「删多少」。

## 安装前：规则和状态各自漂移

没有 Harness 时的日常，问题集中在五处：

- 每个宿主分别维护规则路径和格式，改一处就要同步一遍，漂移是时间问题，不是运气问题；
- 规则文件既承担安全边界，又承担所有操作手册，两种寿命的内容挤在一个文件里，越来越难读；
- 长任务依赖聊天历史续命，上下文压缩或换会话后，目标、进度和验收条件容易丢失；
- 升级个人配置靠脚本直接覆盖文件，失败后没有回退，原状恢复基本靠运气；
- 「Agent 说完成了」和「结果已经机械验证」混为一谈，验收靠信任，不靠证据。

每个问题单独看都不致命，叠在一起就是把工作方式交给运气。这周可能没踩坑；下周换个宿主、开个新任务，
之前攒下的问题就可能一起暴露。

## 安装后：形成一套可维护的工作层

装上之后，同一个现场变成这样：

- 一份宿主中立的 Harness 通过 Adapter 分发到多个 Coding Agent，规则只维护一处，漂移从源头消失；
- 短入口只保留高损失规则和路由，详细流程在需要时才加载，入口永远是地图而不是百科全书；
- Personal overlay 中的 Repository Map 保存有来源的仓库职责与直接关系，跨项目任务可以直接定位
  owner、契约和发布边界，不用靠记忆；
- Memory 保存待核对的线索，Task 保存目标、检查点、验收条件和证据，两者有意分开；
- 安装前可以 dry-run，写入经过预检、锁、staging、备份和失败回滚，每一步失败都有明确退路；
- 能力声明区分已实现、宿主负责和不支持，不把文档建议包装成技术强制，承诺多大就说多大。

## 三个设计的代价

工具文档应该同时写清楚放弃了什么。这三条是主动选择的结果：

- **不做云同步。** 本地优先换来了离线可用和隐私边界，代价是跨设备要靠 `export` / `import` 手动迁移。
  这个选择也意味着没有「账号体系」。你的数据完全在你的机器上，没有服务端可以泄露或丢失。
- **不强制执行。** Markdown 规则只指导行为，真正的强制在代码、schema、测试和宿主权限系统里，
  代价是「写了规则」永远不等于「规则必然被遵守」。规则是给人和 Agent 看的指导，
  不是物理屏障。真正的安全来自多层防护，不是来自「我在文档里写了不许」。
- **不自动学习。** Memory 不会自动升级成规则或写进源码，沉淀必须走提案和复核，代价是你需要偶尔
  亲手确认一次提升。自动升级看似省事，实际容易把一次性上下文误判成长期规则，
  反而污染知识库。手动确认多了一步，但保证了入库内容的质心。

## 它适合什么场景

综合下来，Harnessmith 适合：个人长期维护、跨项目复用的 Coding Agent 工作环境；多宿主并存的日常；
动辄跨会话的长任务；严格的 Git 与发布边界；以及「希望把经验沉淀成可检索文档」而不是无限增长提示词的
使用方式。

反过来，如果你只偶尔用一个 Agent、几行项目说明就够用，直接维护一个简短 `AGENTS.md` 是更轻的正确答案。
它也不是团队级云端控制平台：不提供模型服务、多 Agent 调度或集中式权限系统——那些是另一类工具的职责。

判断要不要用它，可以看三个问题：是否经常在多个 Coding Agent 之间切换？是否积累了一批散落在各处的规则和经验？是否遇到过「任务做到一半状态丢失」或「升级配置覆盖了文件」的情况？如果三个答案都是肯定的，Harnessmith 大概率适合；如果都是否定的，现阶段引入它反而是负担。
