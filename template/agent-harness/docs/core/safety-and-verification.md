# Safety and Verification

## 权限阶梯

1. 安全只读：搜索、读取、状态、diff、日志片段、文档查询。
2. 工作区可恢复修改：源码、测试、配置、文档的最小 patch。
3. 需要确认：越过沙箱、安装依赖、启动 GUI、访问受保护网络或扩大读取范围。
4. 需要明确授权：commit/push/merge/rebase、发布、生产迁移、远端写入、发消息、删除共享资源。

用户要求实现功能通常授权第 1–2 层，不自动授权第 3–4 层。

## 变更安全

- 写前检查 `git status --short`，把用户已有改动视为不可覆盖资产。
- 精确定位文件和范围；不用 broad glob、未解析变量或仓库根执行递归删除。
- 修改生成文件前找到生成源；修改 lockfile 前确认项目包管理规则。
- 不用 `git reset --hard`、`checkout --` 或删除文件来解决不相关脏状态。
- secret、token、cookie、验证码、私钥、生产数据不得进入日志、测试、文档和交付物。

## 验证阶梯

按风险从窄到宽选择，不机械运行全部命令：

1. 静态检查：目标 diff、语法、schema、引用、`git diff --check`。
2. 定向测试：被改模块、回归用例、单个 package 或单条命令。
3. 类型/lint/构建：只扩大到受影响 workspace；项目规则要求时执行。
4. 集成/浏览器/宿主验证：跨边界、UI、网络、桌面或部署路径。
5. CI/共享环境：只在授权与必要时触发。

结果必须区分：

- `passed`：命令实际运行且成功；
- `failed`：可归因的真实失败；
- `not-run`：未执行；
- `inconclusive`：沙箱、网络、凭据、平台或环境使结果不足以下结论。

## 交付证据

交付至少包含：改了什么、为什么、运行了什么验证及结果、哪些未验证、是否存在用户需决定的风险。
不要只说“应该可以”；也不要用海量日志替代结论。
