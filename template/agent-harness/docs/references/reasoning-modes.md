# Reasoning Modes

这是通用 Agent 的按需认知与行动参考，不是每个任务都必须执行的额外流程。路由器会根据用户明确提到的概念，或任务中同时出现的结构信号，自动选择模式；用户不需要知道这些理论的名称。模式不能替代事实核对、权限判断和可执行验证。

## 自动触发协议

`route --json` 的 `reasoningModes` 是执行提示，不是普通的低优先级关键词命中：

1. `activation: inferred` 表示任务结构已经满足该模式的最小触发条件；读取本文件中对应章节，再按其中的行为步骤执行。
2. `activation: explicit` 表示用户明确指定了模式；仍只执行返回的模式，不把整套理论全部叠加到任务上。
3. `matchedSignals` 只是可审计的触发依据，不是需要原样复述给用户的内容。
4. 没有返回模式时，不为了形式套用理论；简单、明确、低风险任务直接按 Playbook 完成。

当返回 `pre-execution-judgment` 时，它优先于实现动作：先完成目标—手段分离和前提审查。只有发现用户方案会显著增加复杂度、成本或风险，或明显偏离目标时，才提出建设性异议并等待确认；低影响的实现偏好直接尊重，不为了展示独立思考而反驳。

模式选择是 guidance，不是宿主或 verifier 的机械保证。执行后仍须用测试、代码、契约、日志或其他可验证证据检查结果。

一次任务通常只启用一个主模式，必要时再加一个风险模式。简单、明确、低风险任务不为了形式执行完整分析。

## 0. 执行前判断

合并目的—手段分离、前提审查、苏格拉底式诘问、建设性异议、字面与精神、奥卡姆剃刀、最小充分方案和反迎合。适用于用户已经指定实现方式，且该方式可能不是目标本身、带有未经验证前提，或可能引入明显额外复杂度的任务。

1. 区分用户真正要达成的目标、用户指定的手段、明确硬约束和未经验证的假设；不要把手段自动升级为目标。
2. 检查当前方案解决的是根因还是表面问题，并提出一个足够满足目标的更简单或更低风险替代方案。
3. 只有在复杂度、成本、风险或目标偏离达到显著程度时，才提出建设性异议；说明当前方案的问题、替代方案、适用条件和推荐选择。
4. 如果用户明确确认该方案是不可变更的偏好或约束，停止争辩并按确认后的方案执行；如果只是低影响实现偏好，直接尊重。
5. 异议不是拒绝执行。未形成显著异议时继续进入 Playbook；需要用户选择时把 `confirmation-needed` 作为停止条件。

最小产物：`goal`、`proposed-means`、`hard-constraints`、`unverified-premises`、`alternatives`、`recommendation`、`confirmation-needed`。

## 1. 问题建模

合并 Surface vs. Root Cause、第一性原理、MECE 和约束识别。适用于目标不清、用户可能带有错误前提、架构需要重构或问题分类容易重复遗漏的任务。

1. 区分表面现象、真正目标、硬约束、非目标和隐含假设。
2. 先列出可观测事实，再从最小前提推导必要条件和候选解释。
3. 只有在分类能减少遗漏或重复时使用 MECE；不要为了形式制造分类。
4. 输出当前理解、关键未知、判断边界和下一步验证。

最小产物：`goal`、`constraints`、`assumptions`、`non-goals`、`next-verification`。

第一性原理不能替代当前代码、配置、测试或用户约束；名称相似也不能证明两个模块存在依赖关系。

## 2. 证据更新

合并贝叶斯推理、证伪主义、科学方法和校准思维。适用于信息不完整、存在多个解释、需要排障或需要证明技术结论的任务。

1. 列出主要假设，不只保留最先想到的解释。
2. 为每个假设寻找支持证据、冲突证据、成立条件和能区分它们的最小验证。
3. 新证据出现后更新判断；优先寻找能够推翻当前结论的反例。
4. 若多个假设仍无法区分，独立检查各自证据，再选择能最大幅度区分它们的验证；不要只重复同一个直觉。
5. 让结论强度与证据强度匹配，区分 `confirmed`、`supported`、`plausible`、`uncertain` 和 `inconclusive`。

没有可靠先验或样本时，不编造精确概率；无法排除关键反例时，不把结论表达为确定事实。

最小产物：`hypotheses`、`supporting-evidence`、`conflicting-evidence`、`next-verification`、`confidence`。

## 3. 失败与后果

合并对抗式审查、逆向思维、事前验尸、二阶思维和反例搜索。适用于安全、权限、并发、数据完整性、外部写入、发布、迁移和不可逆行动。

1. 假设方案已经失败，列出最可能的失败路径。
2. 主动检查边界输入、重复调用、过期状态、权限变化、异常中断和恶意边界条件。
3. 同时分析直接结果、长期副作用、其他参与者的响应和可能形成的新约束。
4. 为每个高风险失败指定检测方式、停止条件、恢复路径和最小修复。
5. 区分已证实缺陷、潜在攻击面和需要真实 Host/环境证据的风险。

没有授权时不执行破坏性操作、远端探测或扩大影响范围。

最小产物：`failure-paths`、`boundary-conditions`、`detection`、`stop-condition`、`recovery`。

## 4. 系统结构

合并系统思维、约束理论、不变量与属性。适用于多组件、多参与者、多阶段流程、状态机、性能、可靠性和跨仓任务。

1. 识别组件、参与者、依赖、输入、输出、延迟和外部边界。
2. 查找反馈回路、局部优化造成的整体副作用和结果延迟。
3. 定位限制整体结果的主要瓶颈；不要平均处理所有问题。
4. 写出合法状态必须满足的不变量，并把可机械表达的属性交给测试、schema 或 verifier。
5. 判断改变一个节点后约束是否会转移到其他节点。

最小产物：`components`、`dependencies`、`boundaries`、`bottleneck`、`invariants`。

## 5. 不确定性决策

合并期望价值、信息价值、最小遗憾、机会成本和决策矩阵。适用于多个方案可行、关键事实未确认或行动可能不可逆的任务。

1. 比较成功收益、失败损失、执行成本、验证成本和时间成本。
2. 判断获取某个未知信息是否可能改变决策；信息价值高于调查成本时先调查。
3. 无法可靠预测时，优先选择可逆、可停止、最大损失较小的方案。
4. 说明选择当前方案放弃了什么机会，以及后续退出路径。
5. 先固定硬门槛和评价标准，再比较真实候选；不要用无来源的精确分数制造客观性。

候选超过两个且结果不可逆时，先生成少量真实候选，用硬约束剪枝，再比较取舍；不要为了形式展开完整决策树。

最小产物：`candidates`、`hard-constraints`、`trade-offs`、`information-value`、`recommendation`。

## 6. 闭环行动

合并 OODA、反馈控制和 PDCA。适用于多次工具调用、外部状态变化、发布、迁移、持续工作流和需要根据结果调整计划的任务。

```text
Observe  读取最新状态和证据
Orient   判断状态是否仍满足目标与约束
Decide   选择最小、可验证、可停止的下一步
Act      执行动作
Feedback 比较实际状态与目标状态，出现偏差就重新规划
```

稳定、重复的流程可以使用 `Plan → Do → Check → Act`；动态外部任务优先使用 OODA。不能沿着最初计划盲目执行到底。

每次动作后必须回到 `Observe`；验证失败时先分类失败原因，再决定修复、重试、阻塞或停止。最多保留一个明确的下一步。

最小产物：`current-state`、`next-action`、`expected-observation`、`verifier`、`recovery`。

## 组合规则

```text
指定复杂实现   → 执行前判断 + 问题建模
理解仓库/架构      → 问题建模 + 系统结构
根因排查           → 证据更新 + 失败与后果
代码/安全评审      → 失败与后果 + 系统结构
方案选型           → 问题建模 + 不确定性决策
发布/迁移          → 失败与后果 + 闭环行动
验证/验收          → 证据更新 + 不变量与属性
```

如果模式之间冲突，事实、用户授权、项目规则和可执行验证优先。模式只改变分析路径，不改变权限、写入边界和交付条件。
